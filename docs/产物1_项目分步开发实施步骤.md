# 产物1：安卓App智能测试Agent系统——分步开发实施步骤与整体思路

> 适用对象：项目开发实施文档（本科毕业设计配套）
> 架构：PySide6 原生桌面 GUI 客户端 + FastAPI 后端服务（C/S 分层，无 WebView）
> 说明：本文档按"串行迭代"顺序组织，每个阶段只做该阶段的事，每一步均附【为什么这么做】。

---

## 一、项目总览与整体思路

### 1.1 项目定位

面向安卓移动端自动化测试的桌面独立软件：用户输入测试需求 → AI Agent 自动完成 RAG 知识检索、生成测试用例、规划 Appium 动作、驱动真机/模拟器执行 UI 测试、采集 ADB 日志与截图、识别 Crash/ANR 缺陷、输出 Markdown 测试报告。

### 1.2 总体架构一句话

**薄客户端 + 厚后端**：Qt 客户端只做"交互、日志展示、进度反馈、报告预览"；Agent、RAG、Appium 调度全部在后端 FastAPI 服务进程内完成，前端通过 HTTP 与后端解耦。

### 1.3 串行迭代路线图（共 10 个阶段）

```
阶段0 需求分析 → 阶段1 基础骨架 → 阶段2 RAG知识库 → 阶段3 工具层
→ 阶段4 Agent核心 → 阶段5 FastAPI服务 → 阶段6 Web页面 → 阶段7 桌面客户端
→ 阶段8 测试联调与异常强化 → 阶段9 打包发布与分发
```

**为什么坚持串行？** 后端模块间存在严格依赖：Agent 依赖工具层与 RAG；服务层依赖 Agent；客户端依赖服务层接口。若并行铺开，接口未冻结前写的代码必然返工。串行迭代让每一阶段结束时都有一个"可运行、可验证"的中间产物。

## 三、分阶段开发实施步骤

### 阶段0：需求分析与边界确认

**任务0-1 需求拆解与可行性验证**
- 任务目标：明确"输入需求→输出报告"主链路与两端职责边界。
- 开发内容：梳理 6 节点业务流；确认外部依赖清单（Appium 服务、安卓设备、LLM API）不可打包、需用户自备；确认密钥不落地的安全约束。
- 验收标准：能用一句话说清每个模块的输入/输出；外部依赖清单评审通过。
- 【为什么这么做】先用最小语言把系统说清楚，避免一上来写代码后接口概念漂移。Appium/模拟器依赖无法塞进 exe，提前声明决定"分发包 + 对方自装环境"的交付形态。
- 需要注意的坑：把"LLM 生成用例质量"当硬指标——原型阶段应定义为"可解析、可执行、可追溯"，质量靠 RAG 上下文与提示词迭代。

---

### 阶段1：基础骨架（目录、日志、配置）

**任务1-1 创建目录树与包骨架**
- 开发内容：按第二节目录树建立空包与 `__init__.py`。
- 验收标准：`python -c "import config, utils"` 通过。
- 【为什么这么做】骨架先行让后续每个文件"有家可归"；`__init__.py` 保证包语义与相对导入正确。

**任务1-2 统一日志 utils/logger.py**
- 开发内容：控制台 + 文件双 handler、统一格式 `%(asctime)s [%(levelname)s] %(message)s`。
- 验收标准：任意模块 `from utils.logger import logger` 打出的日志格式一致。
- 【为什么这么做】多线程 + 多模块系统没有统一日志等于盲飞；统一格式还让桌面端与环形缓冲能用正则/级别解析。
- 坑：Windows 控制台 GBK 编码打印中文乱码——文件日志用 UTF-8，控制台乱码不影响功能（打包后已确认）。

**任务1-3 配置中心 config/settings.py**
- 开发内容：pydantic BaseSettings；LLM 双 provider（qwen/deepseek）参数、Appium/模拟器/真机参数、路径参数；`IS_REAL_DEVICE` 开关；`ANDROID_CAP` 用 `@property` 动态生成。
- 验收标准：`.env` 修改 `IS_REAL_DEVICE` 后，ANDROID_CAP 自动切换 udid/platformVersion。
- 【为什么这么做】配置分散在代码各处是毕设项目最常见的"改一处崩三处"根源；BaseSettings 自动读 `.env` 天然支持"换配置不重打包"。用 `@property` 而非字段，是因为 capability 依赖运行时开关，序列化时也不该把 key 泄漏到repr。
- 坑：`SettingsConfigDict` 默认区分大小写；字段名与 `.env` 键名不一致时静默取默认值——务必写 `.env.example` 对照。

### 阶段2：RAG 知识库模块

**任务2-1 文档加载与切片 rag/document_loader.py**
- 开发内容：txt 读取（utf-8/gbk 容错）、RecursiveCharacterTextSplitter（chunk_size=500, overlap=50）。
- 验收标准：一篇 2000 字文档切出合理片段，无超长块。
- 【为什么这么做】LLM 上下文有限，切片是 RAG 的前提；Recursive 切分器按段落→句子递归回退，比固定长度切分保留语义完整性。
- 坑：overlap 太小导致答案被切断、太大导致冗余；中文场景 500 字左右实测效果均衡。

**任务2-2 向量库 rag/vector_store.py**
- 开发内容：HuggingFaceEmbeddings（all-MiniLM-L6-v2 本地）+ Chroma 持久化（chroma_db/）；模块级单例；`add_documents / top3 相似检索 / rebuild_collection_from_dir`。
- 验收标准：入库后查询"计算器加法怎么测"命中正确片段；重建接口可清空重灌。
- 【为什么这么做】选 Chroma：纯 Python、pip 即用、自带持久化，零部署成本，毕设演示友好（对比：Milvus 需 Docker、FAISS 需自管持久化与元数据）。选本地 embedding 而非调 API：免费、离线、无密钥泄漏面。
- 坑：embedding 模型重复实例化极其耗时——必须单例；Chroma collection 删除后原对象失效，重建要复位单例。

---

### 阶段3：工具层（Agent 的"手"）

**任务3-1 Appium 工具 tools/appium_tool.py**
- 开发内容：`AppiumTool` 类封装 connect/click_by_id/input_text/close；UiAutomator2Options；异常细分（SessionNotCreated/ConnectionError/NoSuchElement/Timeout/StaleElement/InvalidElementState）；构造函数支持设备模式与 UDID 覆盖。
- 验收标准：连接模拟器执行点击成功；未启动 Appium 时返回优雅失败而非崩溃。
- 【为什么这么做】Appium 异常种类繁多，不细分就无法给用户"可行动"的错误提示（如"设备未连接"vs"Appium 未启动"）。会话管理集中在一个类里才能保证 try-finally 全覆盖、绝不泄漏会话占用设备。
- 坑：Appium 崩溃后残留 session 会锁死设备——connect 失败也要清理半初始化 driver；capabilities 键必须带 `appium:` 前缀（W3C 规范），漏前缀报 invalid argument。

**任务3-2 ADB 工具 tools/adb_tool.py**
- 开发内容：subprocess 调 adb：logcat 定长抓取（`-d -t 2000`）、screencap 截图并 pull 到本地、日志读取。
- 验收标准：能稳定拿到崩溃前后的 logcat 文本与截图文件。
- 【为什么这么做】logcat 用 `-d` dump 后即返回，避免流式读取的线程管理复杂度；截图走 `screencap -p /sdcard + pull` 而非 `exec-out` 直读，规避部分设备二进制流污染问题。
- 坑：adb 路径未配置时 FileNotFoundError 要专门提示；subprocess 必须带 timeout 防止设备假死挂死主线程。

**任务3-3 报告工具 tools/report_tool.py**
- 开发内容：Markdown 报告组装（用例/动作结果/缺陷/日志/截图内嵌）、时间戳命名、目录自动创建。
- 验收标准：任意输入下生成合法 Markdown，路径写入 outputs/reports/。
- 【为什么这么做】报告是系统的最终交付物，独立成工具层让节点6保持薄；时间戳命名天然支持历史报告回溯。

### 阶段4：LangGraph Agent 核心

**任务4-1 状态定义 agent/state.py**
- 开发内容：AgentState TypedDict，11 个业务字段 + plan_retry_count + 前端临时密钥/覆盖字段。
- 验收标准：字段覆盖全流程数据需求，无"节点间偷偷传参"。
- 【为什么这么做】状态是图的契约；TypedDict 提供静态检查而不引入运行时开销。临时密钥放进状态而非全局变量，保证"仅本次图执行周期存活"。
- 坑：状态字段全部可覆盖（LangGraph 节点返回部分更新）；不定义默认值的字段在入口必须显式初始化。

**任务4-2 LLM 工厂与调用封装 agent/nodes.py**
- 开发内容：`get_llm(user_api_key, provider)` 双通道（前端临时密钥→新建实例不缓存；.env→按 provider 缓存单例）；`_invoke_llm` 统一异常封装；`_mask_key` 日志脱敏（仅前4位）。
- 验收标准：前端密钥与 .env 密钥两种路径均可出 LLM 结果；日志中无完整密钥。
- 【为什么这么做】工厂模式把"选模型"与"用模型"解耦，双 provider 切换只改配置；临时密钥实例不缓存是安全需求——任务结束引用释放即销毁。
- 坑：`ChatOpenAI` 的 `api_key` 参数优先级高于环境变量，显式传入才不会读到系统里残留的 OPENAI_API_KEY。

**任务4-3 六个节点实现**
- 开发内容：
  1. `rag_retrieve`：需求文本 → 向量检索 top3 → 拼接上下文
  2. `generate_test_case`：系统提示 + RAG 上下文 → 生成结构化用例
  3. `plan_actions`：用例 → JSON 动作列表；markdown 代码块剥离 + 正则提取 + 解析失败**带错误提示重试1次**；重规划时附上一轮失败动作摘要
  4. `execute_test`：try-finally 包裹 Appium 会话；逐步执行动作；adb 抓日志+截图
  5. `reflect_and_detect_defect`：**关键字预扫描**（Crash/ANR/AndroidRuntime，按日志级别过滤）+ LLM 分析；LLM 失效时用关键字证据兜底
  6. `build_report`：调用 ReportTool
- 验收标准：空密钥/LLM 401/Appium 拒连三种降级场景下全链路仍能产出报告。
- 【为什么这么做】节点单一职责：每个节点"读状态→做一件事→写状态"，这是 LangGraph 可重试、可条件路由的前提。plan 节点的重试带错误反馈（而非盲目重试）是提升大模型 JSON 合格率的关键——LLM 看到具体解析错误才能自修正。缺陷检测用"关键字证据 + LLM"双通道而非纯 LLM，是因为大模型对日志幻觉率不可控，真实证据行进 prompt 显著降低误报。
- 坑：LLM 输出 JSON 常被 ```json 包裹或夹带解说——必须多策略解析；日志级别过滤缺失会把 INFO 正常文本误判为 Crash（已实测踩坑修复）。

**任务4-4 图组装与条件重试 agent/graph.py**
- 开发内容：StateGraph 串联 6 节点（START→END）；`execute_test` 后加条件边：全部动作失败且重试额度未用 → 回 `plan_actions`（最多1次）；`run_test_agent` 入口注入初始状态 + 异常兜底返回。
- 验收标准：单测模拟"首轮全失败"路由回 plan、重试后路由到缺陷节点。
- 【为什么这么做】LangGraph 的条件边把"重试策略"从节点内部搬到图结构上，重试次数在状态里可见、可测，比节点内 while 循环干净。入口函数做异常兜底保证 HTTP 层永远拿到可序列化状态。
- 坑：条件边函数不能有副作用（LangGraph 可能多次调用）；状态返回 dict 即可自动合并。

### 阶段5：FastAPI 服务层

**任务5-1 基础路由 api/server.py**
- 开发内容：`POST /upload_doc`（校验格式/大小→切片→入库）、`POST /run_test`（RunTestRequest 校验→同步执行 Agent→返回状态摘要）、`GET /health`。
- 验收标准：Swagger 可完成文档上传与任务执行；非法入参返回 400 友好信息而非堆栈。
- 【为什么这么做】FastAPI 原型规模单文件路由最直观；`RequestValidationError` 处理器把 pydantic 错误翻译成中文逐项提示，是"用户友好"的直接落点。
- 坑：`/run_test` 是同步长任务（分钟级），FastAPI 的 `def` 路由会占用线程池——原型可接受，但必须告知前端"这是长请求"；`python-multipart` 不装则文件上传 415。

**任务5-2 桌面端支撑接口（增量）**
- 开发内容：`GET /api/logs?after_seq=N`（环形缓冲增量日志）、`POST /rebuild_kb`（向量库重建）、`GET /api/config`、`GET /api/last_result`。
- 验收标准：增量拉取 seq 连续无丢失；重建后检索仍可用。
- 【为什么这么做】日志轮询方案完全避开 WebSocket/SSE 的打包复杂度（PyInstaller + uvicorn WebSocket 是已知深坑），且轮询 1s 对演示场景足够实时。

### 阶段6：Web 操作页（轻量演示入口）

**任务6-1 templates/index.html + Jinja2 路由**
- 开发内容：原生 HTML+JS 单页：知识上传、模型/设备/密钥区（password+autocomplete=off）、需求输入、启动任务、结果展示区。
- 验收标准：浏览器全流程操作可完成一次测试任务；密钥刷新即失。
- 【为什么这么做】保留一个"零安装"入口作为答辩备份；原生 JS 不引入构建链，与"禁 WebView、纯原生桌面"的总体思路一致。
- 坑：templates 目录必须用 `resource_path()` 定位，否则打包后 Jinja2 找不到模板（经典 500）。

### 阶段7：PySide6 桌面客户端

**任务7-1 客户端 core 层（config/app_log/icon_maker）**
- 开发内容：RuntimeConfig（密钥仅内存，仅非敏感项持久化）、logging→Qt Signal 桥、QPainter 图标生成。
- 验收标准：dataclass repr 不出现密钥；图标 PNG/ICO 生成成功。
- 【为什么这么做】core 层不依赖 Widget，可在离屏环境单测；Signal 桥是"任意线程日志安全投递 UI"的标准解法（Qt 信号跨线程自动排队）。

**任务7-2 网络层（http_client/api_service/status_worker）**
- 开发内容：QNAM 封装 GET/POST-JSON/multipart（回调主线程触发）；ApiService 高层封装；StatusMonitor QThread 每秒轮询 `/api/logs` 解析"节点N"驱动进度条。
- 验收标准：UI 在任务执行期间可拖动、可点击不卡死。
- 【为什么这么做】两条异步通道各有分工：QNAM 适合请求-响应（其 finished 信号在事件循环线程触发，回调可直接改 UI）；QThread 适合持续轮询（while 循环天然贴合，用 requests 短超时+分片睡眠保证 stop() 秒退）。**任何阻塞调用放主线程都会冻结事件循环 → 界面假死（Windows 判定"未响应"）**，这是硬规则。
- 坑：QNAM reply 必须持有引用否则立即被 GC 中断请求；multipart 的 QFile 生命周期要挂到 reply 上。

**任务7-3 UI 三栏与流程编排**
- 开发内容：QMainWindow + QSplitter 三栏；左 TaskPanel（任务 dataclass 列表，状态着色）、中 LogPanel（QTextCharFormat 四级着色、5000 行截断、导出 txt）、右 ConfigPanel（表单+进度条+状态）；菜单（后端地址/报告预览/关于）。
- 验收标准：新建任务→开始→进度推进→完成弹报告 全流程走通；异常弹窗按网络/Appium/LLM 三类区分。
- 【为什么这么做】三栏对应"管理什么/发生什么/怎么配置"三心智模型；报告预览用 `QTextDocument.setMarkdown()` 原生渲染——零 WebView 满足硬约束，Qt 内置 Markdown 解析器覆盖标题/列表/表格/代码块足够毕设演示。
- 坑：任务状态机在 UI 侧维护（执行中禁止开始按钮）防重复提交；终止任务=客户端 abort 请求（后端同步接口无法优雅取消，需在说明文档讲清语义）。

**任务7-4 客户端离屏烟雾测试 smoke_test.py**
- 开发内容：`QT_QPA_PLATFORM=offscreen` 下实例化全部面板，断言日志渲染/任务增删/状态切换/Markdown 预览/图标。
- 【为什么这么做】GUI 无法用常规单测框架断言，离屏模式让 CI/无显示器环境也能回归。

### 阶段9：打包发布与分发

**任务9-1 后端打包 build_exe.py**
- 内容：PyInstaller onedir + console；`--add-data templates`；hidden-import 补齐（langgraph/uvicorn 子模块等）；copy-metadata 23 项（appium 等运行时读版本元数据）；`--collect-submodules chromadb`（telemetry 动态导入）；清理缓存；产物提示复制 .env。
- 验收标准：目标目录双击 exe → /health、/api/config、首页、/upload_doc 全通。
- 【为什么这么做】onedir 比 onefile 启动快（无解压）、杀毒误报低——演示场景稳定优先。hidden-import/metadata 是 PyInstaller 对动态导入静态分析不到的兜底，必须以"实际运行报什么补什么"的方式迭代。
- 坑：沙箱/权限问题会让 PyInstaller 读不到系统 Python 的 C 扩展（如 unicodedata.pyd）→ 运行时 ModuleNotFoundError，需在干净权限环境构建；uvicorn 必须传 app 实例。

**任务9-2 客户端打包 build_desktop.py**
- 内容：onedir + **windowed**（无控制台）+ 自绘 ICO 图标；hidden-import requests。
- 验收标准：客户端 exe 启动 12s+ 稳定不闪退，能连后端。

**任务9-3 分发物料**
- 内容：`packaging/start_all.bat`（adb 自检→Appium→后端→客户端）、`使用说明.txt`、dist 内预置 .env 与 models_cache（对方免下载模型）。
- 验收标准：压缩 dist 即可发送；接收方按文档 15 分钟内完成环境自装（Node/Appium/adb）。
- 【为什么这么做】Appium(Node)/Android SDK 无法打包进 exe，只能"程序内置 + 环境外装"，一键脚本把四个启动动作收敛成一次双击，显著降低接收方门槛。

## 四、模块调用关系与数据流

```
┌─────────────── 桌面客户端 (desktop/) ───────────────┐
│ UI层(ui/)  ──信号──►  编排(main_window)              │
│     │                     │                          │
│     ▼                     ▼                          │
│ net/api_service ──► http_client ──HTTP──► FastAPI    │
│ net/status_worker ──轮询──► /api/logs                │
└──────────────────────────────────────────────────────┘
                       │
┌──────────────────── 后端服务 ─────────────────────────┐
│ api/server.py ──► agent/graph.run_test_agent         │
│                       │                               │
│            LangGraph 状态机（state.py 契约）           │
│   rag_retrieve → generate → plan ⇄(条件重试) execute │
│                                   → reflect → report │
│        │检索            │LLM工厂        │工具调用      │
│   rag/vector_store   agent/nodes    tools/appium_tool│
│        │             (get_llm)      tools/adb_tool   │
│        ▼                                   ▼          │
│   chroma_db/ + models_cache/          设备/Appium服务  │
│   utils/log_buffer ◄── 全部模块的 logger 输出          │
└──────────────────────────────────────────────────────┘
```

**分层设计理由**：
- 依赖单向：`api → agent → tools/rag → config/utils`，上层知道下层、下层不知道上层，任何层可独立替换（如把 Chroma 换 FAISS 只动 rag/）。
- 接口契约显式：Agent 间契约是 AgentState；前后端契约是 JSON 路由（Pydantic 校验）；线程间契约是 Qt 信号签名。三处契约清楚，联调才快。
- 核心接口定义：
  - `run_test_agent(requirement, qwen_api_key=None, deepseek_api_key=None, llm_provider=None, is_real_device=None, real_udid=None) -> AgentState`
  - `AppiumTool.connect()->bool / click_by_id(id)->bool / input_text(id,text)->bool / close()`
  - `AdbTool.grab_logcat()->str / take_screenshot()->str路径 / read_log()->str`
  - `GET /api/logs?after_seq=N -> {logs:[{seq,ts,level,message}], last_seq}`

## 五、风险与坑位清单汇总

| # | 坑 | 后果 | 对策（已落地） |
|---|---|---|---|
| 1 | uvicorn 字符串导入方式启动 | 打包后启动失败 | 传 app 实例 |
| 2 | 相对路径读资源/写数据 | exe 中路径不存在 | resource_path/data_path 双函数 |
| 3 | LLM 输出非纯 JSON | 动作解析失败 | 代码块剥离+正则+带错误重试 |
| 4 | 日志 INFO 级含 crash 字样 | 缺陷误报 | 按级别过滤关键字扫描 |
| 5 | Appium 会话泄漏 | 设备占用死锁 | try-finally + 失败清理 |
| 6 | embedding 模型重复加载 | 每次检索慢 10s+ | 模块级单例 |
| 7 | QNAM reply 无引用 | 请求被 GC 中断 | 调用方持有引用 |
| 8 | UI 线程做网络/阻塞调用 | 界面假死 | QNAM 异步 + QThread 轮询 |
| 9 | PyInstaller 动态导入缺失 | exe 运行 ModuleNotFoundError | hidden-import + copy-metadata + collect-submodules |
| 10 | 沙箱拦截读取系统 Python | stdlib C 扩展收集不全 | 干净权限环境构建 |
