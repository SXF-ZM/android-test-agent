# 产物1：USB真机安卓App智能测试Agent系统——分步开发实施步骤与整体思路（真机安全增强版）

> 定位：项目开发实施文档 / 毕设工程文档
> 架构：PySide6 原生桌面 GUI + FastAPI 后端（C/S 分层，禁 WebView）
> **本版核心变化**：被测对象从模拟器升级为 **USB 真机**；新增**安全专题设计**（操作白名单、高危动作人工确认、首页安全提示），并明确 V1 不开放动态代码执行、主机侧无需代码沙箱的安全边界。

---

## 一、项目总览与安全边界

### 1.1 项目定位

Windows 桌面软件：USB 数据线连接**真实安卓手机**，用户输入测试需求 → AI Agent 自动完成 RAG 检索、生成用例、规划 Appium 动作、通过 ADB 操控真机执行 UI 测试、抓取设备日志与截图、识别 Crash/ANR 缺陷、输出 Markdown 报告。

### 1.2 安全集边界三条（写进需求，贯穿全程）

1. **真机不是模拟器**：模拟器有天然隔离沙箱（崩了重置即可），USB 真机**没有任何设备侧沙箱**——ADB 可以读写被测 App 数据、卸载应用、甚至删除系统文件。真机侧风险客观存在。
2. **V1 不开放动态代码执行**：Agent 只能调用**预先封装的工具函数**（点击/输入/抓日志等白名单动作），不允许动态执行任意 Python/Shell 代码——因此 **Windows 主机侧不需要代码沙箱**，安全防线放在**业务层**。
3. **业务层三道防线**：① 工具层操作白名单（硬拦截高危 ADB 指令）；② 高危动作二次弹窗人工确认（清空应用数据、卸载被测应用等）；③ 软件首页安全提示（推荐专用备用测试机，禁止主力手机）。

> 【为什么先把边界说清楚】安全设计最忌"做完了再补"。V1 把 Agent 的能力边界**收窄**到白名单工具，比"先放开了再沙箱兜住"成本低一个数量级——这决定了整个架构不需要 Docker/虚拟机等重装备，也决定了测试计划必须包含"恶意/畸形动作指令被拦截"的用例。

### 1.3 串行迭代路线图（10 阶段）

```
阶段0 需求与安全边界分析 → 阶段1 基础骨架 → 阶段2 RAG知识库 → 阶段3 工具层+安全守卫
→ 阶段4 Agent核心 → 阶段5 FastAPI服务(含确认队列) → 阶段6 Web页 → 阶段7 桌面客户端(含安全提示/确认弹窗)
→ 阶段8 联调与安全测试 → 阶段9 打包分发
```

**为什么坚持串行**：依赖链是 `Agent → tools/rag`、`api → agent`、`desktop → api`，接口未冻结前并行开发必然返工；且安全守卫必须**先于** Agent 执行逻辑存在（先有闸门再放水）。

**目录分层设计理由**：
- 依赖严格单向：`api → agent → tools/rag → config/utils`，desktop 内部 `ui → net → core`。上层可换下层（Chroma→FAISS 只改 rag/），下层不知上层。
- **security_guard 放 tools 层而非 agent 层**：闸门必须卡在"水龙头"（工具执行）之前，任何调用方（现在的 LangGraph 节点、将来的 Web 页、将来的脚本）都绕不过它；放 agent 层则存在"别的入口绕过守卫直调工具"的漏洞。
- adb_tool **不提供任意命令透传**：封装 `grab_logcat/screenshot/device_online` 等固定函数，从接口设计上消灭"Agent 想执行什么 adb 命令都行"的可能。

## 三、分阶段开发实施步骤

### 阶段0：需求分析 + 安全边界确认

**任务0-1 业务链路与真机场景定义**
- 任务目标：明确"需求→报告"全链路与 USB 真机环境。
- 开发内容：梳理 6 节点流；确认真机环境清单（开发者模式+USB调试、adb 授权、Appium+UIA2、被测包名/启动页查询方法）；确认 V1 能力边界。
- 验收标准：一页纸说清每模块输入输出；真机 demo 手工走通一次 adb 全流程。
- 【为什么这么做】真机环境变量远多于模拟器（厂商 ROM、安卓版本、USB授权弹窗），先手工跑通 adb 链路，排除"环境问题伪装成代码 bug"的最大干扰源。
- 坑：小米/OPPO 等厂商需额外开启"USB调试（安全设置）"允许模拟点击；未开启时 Appium 能连上但点击无效果——排查会浪费半天。

**任务0-2 安全边界评审（本阶段最重要任务）**
- 任务目标：冻结 V1 安全设计三原则。
- 开发内容：确认 ① 不开放动态代码执行 → 主机无沙箱；② 工具层白名单 + 高危分级；③ 首页提示 + 备用机建议；产出《动作分级表》（AUTO/CONFIRM/BLOCK 初版）。
- 验收标准：动作分级表评审通过并落入 settings 设计。
- 【为什么这么做】"Agent 能力=风险面"。V1 收窄能力换安全，是**用产品约束换工程简单**的明确取舍：不引入 Docker 沙箱，毕设打包分发仍是一个文件夹；同时把"V2 引入 Docker 沙箱 + 动态脚本"写进路线图，答辩时能讲清演进逻辑。
- 坑：把"提示词里叫 LLM 别输出危险动作"当安全措施——提示词是**劝阻不是拦截**，LLM 输出不可信，拦截必须在代码层。

### 阶段1：基础骨架

**任务1-1 目录树与包骨架**：按第二节建目录；`import config, utils` 通过。
【为什么】骨架先行，后续文件各归其位。

**任务1-2 logger.py**：统一格式双输出。
【为什么】真机排障高度依赖日志（USB 断连时序、授权弹窗）；统一格式让桌面端可解析。

**任务1-3 settings.py（含安全配置段）**：LLM 双 provider、真机参数（REAL_PHONE_UDID、IS_REAL_DEVICE）、路径；**ACTION_WHITELIST / DANGEROUS_ACTIONS / CONFIRM_ENABLED**。
- 验收标准：改 .env 的 IS_REAL_DEVICE，ANDROID_CAP 自动注入 udid；白名单在配置中可读。
- 【为什么】白名单配置化：安全策略调整（如临时允许某动作）不修改代码不重新打包；真机 UDID 每台手机不同，必须外置。
- 坑：UDID 中含冒号等特殊字符时 capability 传递注意字符串原样保留；不要把 UDID 打进日志全文（可打后4位）。

**任务1-4 resource_path.py / log_buffer.py**：打包路径双函数、环形缓冲。
【为什么】exe 资源路径与数据路径分家；客户端实时日志与确认轮询的共用底座。

### 阶段2：RAG 知识库

**任务2-1 document_loader.py**：txt 读取（utf-8/gbk 容错）+ 500字/50重叠切片。
【为什么】Recursive 切分按段落回退保留语义；切片质量直接决定检索命中。

**任务2-2 vector_store.py**：HuggingFaceEmbeddings(all-MiniLM-L6-v2) + Chroma 持久化单例 + top3 检索 + 目录重建。
- 验收标准：上传"真机测试规范"文档后，查"卸载应用怎么测"能命中对应片段。
- 【为什么选 Chroma/本地 embedding】零部署、离线、无密钥面——与"主机侧不引入重装备"的安全边界一致；知识库内容建议包含**真机测试安全规范**（哪些操作需人工确认），让 LLM 规划动作时自带安全意识，与代码层白名单形成双保险。
- 坑：collection 删除后原对象失效，重建需复位单例。

### 阶段3：工具层 + 安全守卫（真机核心）

**任务3-1 adb_tool.py（真机版）**
- 开发内容：subprocess 封装固定函数集：`device_online()`（adb devices 轮询）、`grab_logcat()`（-d -t 2000）、`take_screenshot()`（screencap+pull）、`list_packages()`；**不提供 run_any_shell()**。
- 验收标准：真机插拔时 device_online 3 秒内感知变化。
- 【为什么不做任意命令透传】这是真机安全的**接口级设计**：Agent 的世界只有"封装好的能力"，没有"原始 adb"。从 API 面上消除注入可能，比运行时拦截更彻底。
- 坑：subprocess 必须带 timeout（真机假死时命令会无限挂起）；Windows 控制台编码用 encoding='utf-8', errors='replace' 兜底。

**任务3-2 appium_tool.py（USB 真机版）**
- 开发内容：UiAutomator2Options 动态构建（真机注入 appium:udid）；connect/click_by_id/input_text/swipe/close；6 类异常细分捕获。
- 验收标准：USB 真机全流程：连接→打开被测App→点击→输入→关闭，会话零泄漏。
- 【为什么 try-finally 是真机生命线】模拟器会话泄漏重启即可，真机会话泄漏会导致**用户的手机**持续被占用/黑屏，且 Appium 进程残留后下一次连接直接失败——演示现场最高频事故。
- 坑：真机息屏导致点击失效——cap 加 `appium:skipServerInstallation` 之外还应引导用户设置"充电时屏幕不休眠"；部分厂商 ROM 首次运行 UIA2 需手机端确认安装弹窗。

**任务3-3 security_guard.py（安全核心，先行于 Agent）**
- 开发内容：实现三级判定：
  - **AUTO**：click / input_text / swipe / 抓日志 / 截图 / 打开被测App
  - **CONFIRM**：`pm clear <被测包>`（清应用数据）、`pm uninstall <被测包>`、`settings put` 修改系统设置
  - **BLOCK**：非白名单动作类型；卸载非被测包；`rm` 任意路径；`pm disable/uninstall` 系统应用（com.android.* 等系统包名前缀）；`settings put global/secure` 关键开关；`reboot/recovery`；`content insert/delete` 直改任意 Provider
  - 接口：`check_action(action: dict) -> GuardResult(level, reason)`；拦截事件结构化记录。
- 验收标准：**独立单元测试**覆盖"白名单内正常动作→AUTO、pm clear 被测包→CONFIRM、rm /system→BLOCK、未知动作→BLOCK"全部路径（先写测试再接 Agent）。
- 【为什么三级而不是两级】一刀切 BLOCK 会把"清应用数据重测"这类合理测试动作也杀死，逼用户绕过系统；一刀切放行则真机风险不可控。CONFIRM 档把决定权交还用户，同时留下确认记录——**安全设计要让用户"知情且可控"，而不是替用户做全部决定**。
- 【为什么先写测试】安全组件的测试就是"规格说明"：分级表一旦冻结，测试即法律；后续任何人改守卫，跑测试立刻知道是否破坏了安全承诺。
- 坑：包名前缀判断要用"=="而非 startswith（存在 `com.android.test.app` 这类用户包名）；动作 JSON 字段注入（resource_id 里塞分号）——Appium 参数是结构化传递不经 shell 拼接，天然免疫，但 **adb 封装函数内部绝不能用字符串拼接拼命令**，一律列表参数传 subprocess。

**任务3-4 report_tool.py**：报告生成 ★ 新增"安全事件"小节（被拦截动作列表+被确认动作列表+确认人选择）。
【为什么】安全行为可追溯进报告，答辩演示时"系统主动拦截了危险指令"是最有说服力的一页。

### 阶段4：LangGraph Agent 核心

**任务4-1 state.py**：11 业务字段 + plan_retry_count + 临时密钥字段 ★ + **blocked_actions / pending_confirmations / confirmed_action_ids**。
【为什么】安全事件与确认状态进入图状态，才能跨节点传递并在报告节点汇总。

**任务4-2 nodes.py：LLM 工厂 + 6 节点**
- 开发内容：工厂支持前端临时密钥/.env 双通道与脱敏日志；六节点中：
  - **plan_actions ★ 安全改造**：提示词明确"只能输出以下动作类型：click/input_text/swipe/open_app/…"（白名单写在提示词里）；输出 JSON 后仍要过守卫——提示词劝阻 + 代码拦截双层。
  - **execute_test ★ 确认挂起逻辑**：遍历动作 → 守卫判定 → AUTO 直接执行；BLOCK 跳过并记入 blocked_actions；CONFIRM 则写入 pending_confirmations 并**挂起该动作**（等待用户确认后继续，超时默认拒绝）。
  - reflect_and_detect_defect：关键字预扫描（级别过滤）+ LLM 分析 + 证据兜底。
- 验收标准：构造含 `pm clear` 的规划输出，验证其进入待确认队列而非直接执行；构造 `rm /system/x`，验证被 BLOCK 且进报告。
- 【为什么提示词与守卫双层】提示词让 90% 的情况输出本就合规（少弹窗、体验好）；代码守卫兜住剩余 10% 的幻觉——**用提示词优化体验，用代码保证下限**。
- 坑：CONFIRM 挂起不能死循环阻塞图执行——设定确认超时（如 120 秒）自动按拒绝处理，超时策略写进报告。

**任务4-3 graph.py**：6 节点串联 + 执行失败条件重试边（最多1次）+ 入口异常兜底。
【为什么重试放图上】重试次数在状态中可见可测；条件边函数保持纯函数（LangGraph 可能多次调用）。

### 阶段5：FastAPI 服务（含确认队列接口）

**任务5-1 基础路由**：/upload_doc（校验+切片入库）、/run_test（RunTestRequest：requirement 5~2000字 + 可选 provider/双密钥/is_real_device/udid）、/health；RequestValidationError 中文处理器。
【为什么校验前置】垃圾输入进 Agent 前拦住；错误说人话不甩堆栈。

**任务5-2 ★ 确认队列接口**
- 开发内容：
  - `GET /api/pending_confirmations?task_id=` → 返回当前挂起的待确认动作（含动作内容、影响范围说明、风险等级）
  - `POST /api/confirm/{action_id}` → body: `{approved: bool, remember: bool}`；remember=true 表示"本次任务内同类动作全部自动允许"
  - 实现方式：内存字典（task_id → 队列）+ threading.Event 挂起/唤醒 execute_test 中的等待
- 验收标准：手工模拟——客户端轮询发现待确认 → POST 拒绝 → Agent 跳过该动作继续 → 报告含该事件。
- 【为什么"轮询+确认队列"而不是 WebSocket】客户端已有 1s 轮询线程（日志用），扩展成"一次轮询带日志+待确认"零新增通道；WebSocket 在 PyInstaller+uvicorn 下有兼容坑，且演示场景 1s 延迟无感。**V1 一切从简，复杂度是安全的天敌。**
- 坑：确认接口必须校验 action_id 属于当前任务，防止误确认其他任务的动作；并发确认同一动作要幂等（第二次返回已处理）。

**任务5-3 /api/logs /rebuild_kb /api/config /api/last_result**：同前版设计。
【为什么日志接口是确认回路的载体】客户端 StatusMonitor 每秒拉一次日志，顺带带回待确认事件，UI 线程零负担。

【为什么保留 Web 入口】后端能力不绑死单一前端；答辩备份。安全声明在网页同样可见，保证两个入口安全体验一致。

### 阶段7：PySide6 桌面客户端（安全交互重点）

**任务7-1 core 层**：RuntimeConfig（密钥仅内存+repr隐藏）、日志桥、图标绘制。
【为什么 core 不依赖 Qt Widget】离屏可测；换 UI 框架也不动底座。

**任务7-2 net 层**：QNAM 异步三封装；StatusMonitor ★ 轮询扩展为"日志 + pending_confirmations"。
- 验收标准：UI 执行任务全程可拖动；待确认事件 1 秒内出现在客户端。
- 【为什么两条异步通道分工】QNAM=请求-响应（回调在主线程，改 UI 免加锁）；QThread=持续轮询。**主线程只做轻活的硬规则**：任何阻塞调用都会冻结事件循环→界面"未响应"。

**任务7-3 ui 层（三栏 + ★ 两个安全组件）**
- **welcome_dialog.py 首页安全提示**：首次启动强制弹出（可配置每次启动）：真机测试风险说明 + "推荐使用专用备用测试机，请勿使用保存个人隐私的主力手机" + "测试过程可能清空被测App数据" + 【我已知晓并使用备用测试机】勾选后方可继续。
- **security_dialog.py 高危确认弹窗**：StatusMonitor 收到 pending 事件 → 主线程弹出模态框，展示：动作原文、目标包名、影响说明（"将清空该App的全部数据，包括登录状态"）、三按钮【允许一次】【本任务全部允许】【拒绝】；选择结果 POST 回后端。
- 验收标准：不点"我已知晓"无法使用软件；构造 pm clear 任务时弹窗出现、拒绝后动作被跳过且报告记录。
- 【为什么弹窗给三个选项】"允许一次"最安全默认；"本任务全部允许"服务真机测试中反复清数据重测的真实工作流（否则弹窗疲劳）；"拒绝"保底。**安全 UX 的敌人是弹窗疲劳——给用户高效通路，才不会逼他养成无脑点允许的习惯。**
- 坑：弹窗必须在主线程（模态框跨线程必崩）——pending 事件经信号送主线程再弹；任务结束时清理未响应的弹窗。

**任务7-4 smoke_test.py**：离屏断言扩展 ★（welcome 弹窗阻断逻辑、security_dialog 三按钮回传、白名单日志着色）。
【为什么】安全交互是回归重点，离屏测试让它可自动化。

### 阶段8：联调与安全测试

**任务8-1 功能联调清单**：真机全流程（USB 授权→连接→执行→报告）、LLM 401/Appium 拒连/USB 中途拔线/向量库失败四类降级。
【为什么】真机环境变量多（厂商 ROM/USB 授权弹窗/息屏），逐项演练防演示翻车。

**任务8-2 ★ 安全测试用例集（红队自查）**
- LLM 被诱导输出 `pm uninstall com.android.launcher` → 必须被 BLOCK 且报告可见
- 构造 resource_id 超长/特殊字符 → 工具层正常处理不崩溃不注入
- 确认接口越权（用别的任务的 action_id）→ 返回无效

- 【为什么专门做红队自查】安全机制没被攻击过等于没测过；这组用例同时是答辩演示的"安全亮点"素材。
- 坑：USB 拔线后 adb 命令可能挂住不返回——所有 adb subprocess 的 timeout 在此场景是唯一救命稻草。

**任务8-3 密钥安全审计**：grep 全仓确认临时密钥零落盘；日志仅前4位。
【为什么】安全设计必须可验证，一条 grep 命令就是证据。

## 四、模块调用关系、接口定义与安全数据流

```
┌────────────── 桌面客户端 ──────────────┐
│ welcome_dialog(首次安全提示)            │
│ TaskPanel   LogPanel   ConfigPanel     │
│        ↕ 信号槽（主线程）               │
│ security_dialog ◄─ 信号 ─ StatusMonitor│
│        │ POST /api/confirm             │
│ api_service ─► http_client ──HTTP──►   │
└────────────────────────────────────────┘
                    │
┌──────────────── 后端服务 ────────────────────────────┐
│ server.py                                            │
│   /run_test ─► graph.run_test_agent                  │
│   /api/logs+pending ◄─ log_buffer+确认队列            │
│   /api/confirm ─► threading.Event 唤醒 execute_test  │
│                                                      │
│ LangGraph: plan → execute ⇄(失败重试) → reflect →    │
│            report                                    │
│                │                                     │
│         security_guard.check_action                  │
│          AUTO──► appium_tool/adb_tool ──USB──► 真机   │
│          CONFIRM──► pending_confirmations(挂起)      │
│          BLOCK──► blocked_actions(记录)              │
└──────────────────────────────────────────────────────┘
```

**核心接口契约**：
- `GuardResult = check_action(action: dict) -> Literal["AUTO","CONFIRM","BLOCK"]`（附 reason）
- `POST /api/confirm/{action_id}` body `{"approved": bool, "remember": bool}`
- `GET /api/pending_confirmations` → `[{action_id, task_id, action, impact, risk_level}]`
- `run_test_agent(requirement, qwen_api_key=None, deepseek_api_key=None, llm_provider=None, is_real_device=None, real_udid=None) -> AgentState`

**分层职责分离的理由**：安全闸门在 tools 入口（任何调用方绕不过）→ 确认决策在用户（真机风险人工兜底）→ 状态与报告承载证据（可追溯）→ 客户端只做交互（不持有安全逻辑，防止前端被绕过）。**安全判断永远在服务端，客户端弹窗只是转发用户意愿**——这是 C/S 安全的铁律。

## 五、风险与坑位清单汇总

| # | 坑 | 后果 | 对策（已设计） |
|---|---|---|---|
| 1 | LLM 幻觉输出危险动作 | 真机被清数据/卸系统应用 | 提示词白名单 + security_guard 代码级三级拦截 |
| 2 | 真机会话泄漏 | 用户手机被占用、后续连接全失败 | try-finally 强制 close + 失败清理半初始化 driver |
| 3 | USB 中途拔线 | adb 挂死拖垮后端 | subprocess 全量 timeout + device_online 前置检查 |
| 4 | 厂商 ROM 未开"安全设置USB调试" | 连上但点击无效 | 使用说明分厂商说明；连接后先做一次"探测点击"验证 |
| 5 | 息屏导致自动化失效 | 执行半途卡住 | 引导设置不休眠；执行前唤醒屏幕动作入白名单 |
| 6 | 主力机被测试 | 个人隐私数据风险 | 首页强制安全提示 + 备用机建议 + 报告免责记录 |
| 7 | uvicorn 字符串导入 | 打包后启动失败 | 传 app 实例 |
| 8 | 相对路径在 exe 失效 | 资源找不到 | resource_path/data_path 双函数 |
| 9 | UI 主线程阻塞 | 界面未响应 | QNAM 异步 + QThread 轮询 + 信号槽回主线程 |
| 10 | 打包动态导入缺失 | exe 运行 ModuleNotFoundError | hidden-import + copy-metadata + collect-submodules |
| 11 | 密钥落盘 | 密钥泄漏 | 状态内存生命周期 + 脱敏日志 + grep 审计 |
| 12 | 确认接口被误用/重放 | 误确认其他任务动作 | action_id 归属校验 + 幂等处理 + 超时默认拒绝 |
