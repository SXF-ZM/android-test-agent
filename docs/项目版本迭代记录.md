## 二、V1.3.0 工程化增强版（2026-10-31，当前）

本版本不改变“RAG → 生成用例 → 规划动作 → 执行 → 缺陷分析 → 报告”的主链路，重点解决四类工程问题：**敏感信息泄露、产物互相覆盖、日志噪声干扰、LLM 输出不稳定**。

### 2.1 输入脱敏与静态安全闸门

**新增文件**

- [utils/redaction.py](../utils/redaction.py)：统一脱敏入口，提供 `mask_text`、`redact_action_params`、`redact_action_item`、`redact_text_in_message`。
- [agent/schemas.py](../agent/schemas.py)：动作与缺陷的 Pydantic/参数校验，非法条目不进入执行与报告。

**行为变化**

- `input_text` 内容在日志、动作结果、重规划提示词、Markdown 报告中统一显示为 `[已输入 N 个字符]`，脱敏幂等，不会二次包装。
- 驱动/协议异常信息若回显输入内容，也会在写日志和返回结果前替换，避免 `sendKeys`/MCP 错误信息泄露原文。
- Appium 与 mobile-mcp 后端在动作执行前增加静态检查：
  - 密码/验证码类输入框拒绝输入；
  - 购买、订阅、支付、分享、发送等敏感控件拒绝点击；
  - 逐步模式下坐标点击默认必须命中当前 UI 树中已解析的可点击节点，未命中时拒绝执行。
- 新增配置 `STEPWISE_ALLOW_UNTARGETED_TAP=false`；只有显式改为 `true` 才允许未命中节点的坐标点击。

**涉及文件**

- [tools/mobile_mcp_tool.py](../tools/mobile_mcp_tool.py)

### 2.2 run_id 产物隔离与执行轨迹合并

**新增文件**

- [utils/run_context.py](../utils/run_context.py)：生成 `run_id`，创建并校验单次任务产物目录。

**目录变化**

```text
outputs/runs/<run_id>/
├── logs/
├── screenshots/
└── reports/
```

- 每次任务生成独立 `run_id`，日志、截图、报告不再写进公共目录，多次测试互不覆盖。
- `/run_test` 响应新增 `run_id`；`/api/last_result` 同步返回 `run_id`。
- Markdown 报告文件名为 `test_report_<run_id>.md`，报告顶部展示任务 ID。
- 执行失败后触发的重规划不会再覆盖首轮结果：`execute_results` 仍表示“当前/最后一轮”，用于 LangGraph 路由；新增 `execute_attempts` 保存每一轮的动作、模式和异常。
- 报告新增“执行尝试次数”“异常与诊断”区块，多次尝试按轮次分别展示。
- 设备预检失败、驱动初始化失败、连接失败等早期异常也会写入一次执行尝试，并生成带诊断信息的报告。

**重建语义修正**

- `rag/vector_store.rebuild_collection_from_dir()` 失败时抛出 `RuntimeError`，不再用返回值 0 混淆“空目录”和“重建失败”。
- `/rebuild_kb` 对真实失败返回 500；空目录仍返回成功但入库数为 0。

**上传文件名校验**

- `/upload_doc` 对上传文件名统一路径分隔符、只取 basename，并追加时间戳与随机后缀，避免路径穿越和同秒覆盖。

### 2.3 日志按 PID/级别过滤与 LLM 调用韧性

**日志过滤**

- [tools/adb_tool.py](../tools/adb_tool.py) 新增 `get_app_pids()`：通过 `ps -A` 匹配被测包名及其子进程，失败时回退 `pidof`。
- 执行动作前记录一次 PID，执行后再次记录，前后 PID 取并集，覆盖 App 崩溃重启后 PID 变化的情况。
- `extract_relevant_log()` 仅保留：
  - 被测应用 PID/包名相关的 W/E/F/A 级别日志；
  - 含 Crash/ANR/AndroidRuntime 等缺陷关键字的行。
- 过滤结果为空时才回退完整日志尾部，避免短日志测试混入无关噪声。
- logcat 抓取显式使用 `main,system,crash` 三个缓冲区，失败时回退默认缓冲区。

**LLM 调用**

- 新增配置：
  - `LLM_REQUEST_TIMEOUT`（默认 60 秒）
  - `LLM_MAX_RETRIES`（默认 2 次）
  - `LLM_RETRY_BACKOFF_SECONDS`（默认 1.5 秒，按 2 倍指数退避）
- `ChatOpenAI` 显式设置 `timeout`，关闭 SDK 内部重试，由应用层统一控制重试节奏。
- 401/403/404/422 等认证、权限、参数错误不重试；408/409/425/429/5xx 与网络异常按退避策略重试。
- JSON 数组提取改用 `json.JSONDecoder.raw_decode` 扫描，不再依赖贪婪正则。
- 动作输出逐条校验：缺少 `resource_id`、未知动作、非法参数、超范围 `sleep` 等会被丢弃并触发带错误提示的重试。
- 缺陷输出通过 `DefectItem` 归一化类型、严重级别和文本字段；显式空数组视为“无缺陷”，不再误报解析失败。

### 2.4 兼容性与验证

- `execute_results` 的原语义保持不变，LangGraph 条件边无需修改。
- `capture_logcat`、`capture_screenshot`、`generate_markdown_report` 新增参数均为可选，旧调用方式仍可用。
- 桌面客户端通过 `data.get(...)` 读取响应，新增 `run_id` 不影响旧字段。
- 已完成验证：全项目 `compileall`、核心模块导入、脱敏幂等性、动作/缺陷校验、JSON 提取、报告多尝试展示、空目录与重建失败语义、密码/敏感控件拦截等纯函数与 mock 测试。
- 当前环境没有可用安卓设备、Appium 服务和 mobile-mcp 运行环境，**尚未完成真机端到端回归**。

| 配置 | 默认值 | 说明 |

| `LLM_REQUEST_TIMEOUT` | `60` | 单次 LLM 请求超时秒数 |

## 三、V1.2.0 双后端与逐步 UI 驱动版

**迭代背景**

静态动作规划只依据测试用例文本推断 resource-id，遇到多邻国、Compose/Flutter 等动态页面时，可点击容器往往没有 resource-id，文字又落在不可点击的子节点上，导致大量点击落空。

**主要变更**

- 抽象 `DeviceDriver` 协议，统一 Appium 与 mobile-mcp 两套执行后端。
- 新增 mobile-mcp 后端，通过 MCP 调用 `mobile_list_elements_on_screen`、`mobile_click_on_screen_at_coordinates`、`mobile_type_keys` 等工具。
- 新增逐步 UI 驱动模式：
  - 每步读取实时 UI 树，裁剪并标记可点击节点；
  - LLM 选择 `tap_by_ref`、`tap_by_text`、`tap_by_coordinates`、`input_text`、`press_back`、`scroll`、`sleep`、`done`；
  - 执行后重新观察页面，直到目标达成或达到步数/时间上限。
- 增加无进展保护：同一控件连续多次操作后页面无变化时阻止继续重复动作。
- `done success=true` 要求证据真实出现在当前 UI 树中，课程类目标还要求出现“完成/连击/经验”等结算语义，避免把反馈页的“继续”误判为整节课完成。
- 多用例逐条规划，并在用例之间自动插入 `restart_app` 复位 App。
- Web 与桌面端支持按单次任务覆盖模型、后端、设备模式、UDID、包名和 Activity。

## 四、V1.1.0 真机安全增强版

**迭代背景**

被测对象从模拟器升级为 USB 真机。模拟器崩溃后可重置，真机没有设备侧沙箱，必须在业务层收窄 Agent 能力边界。

**主要变更**

- 支持 `IS_REAL_DEVICE=true/false` 切换真机/模拟器，真机自动注入 UDID capability。
- 支持前端单次任务覆盖设备模式、UDID、被测应用包名和启动 Activity。
- UI 树只保留被测应用包名内的节点，过滤系统 UI 与其他应用节点。
- 密码字段文本强制显示为 `[密码字段已隐藏]`，执行层拒绝向密码字段输入内容。
- 购买、订阅、支付、分享、发送消息等敏感控件标记 `danger=true`，执行层默认拒绝点击。
- 形成真机安全设计文档：操作白名单、高危动作人工确认、首页安全提示等；其中人工确认队列属于设计扩展点，当前代码以 UI 层拦截、输入脱敏和静态安全闸门为主。

## 六、版本维护约定

后续每次迭代按以下顺序更新，避免文档与代码脱节：

1. 在代码中完成功能，并保留向后兼容或明确迁移说明；
2. 在本文件顶部更新“当前版本”，新增对应版本小节，写清变更点、涉及文件、配置、验证结果和未完成项；
3. 更新 [README](../README.md) 的版本号与版本总览；
4. 更新开发实施文档中的阶段任务和验收标准；
5. 更新教学文稿中的原理讲解与课后练习；
6. 如涉及部署方式，同步更新 [packaging/使用说明.txt](../packaging/使用说明.txt)。

版本号建议采用 `主版本.次版本.修订号`：

- 主版本：架构或使用方式发生不兼容变化；
- 次版本：新增能力，向后兼容；
- 修订号：缺陷修复、文案和配置修正。
